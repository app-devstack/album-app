## 問題と解決（第三者向け要約）

**問題**: 出先や通信制限下で写真をアップロードするとモバイルデータ料金がかかる。一方で「Wi-Fi になるまで待つ」だけだと、ユーザーが後からアプリを開き直す手間が残る。Web（ブラウザ / PWA）のままでは、特に iOS でアプリ終了後のバックグラウンド送信ができず、この二つを同時に満たせない。

**解決**: 現行の Cloudflare / Web アプリはそのまま活かし、**React Native でネイティブシェルを被せる**。写真は端末側にキューし、OS のバックグラウンド転送（Wi-Fi / 非従量回線制約つき）で R2 へ送り、完了後に既存 API でメタデータを登録する。

**経緯（1行）**: 通信料を抑えたい声に対し Web だけで Wi-Fi 待ちを検討したが、再オープン不要まで含めるとネイティブ実行環境が必要と判明したため本計画に切り替えた。

---

## What（何を解決したいか）

1. **モバイルデータ通信料をかけずに**、ユーザーが選んだ写真・動画をアルバムへ届けられること  
2. Wi-Fi（または非従量回線）に繋がったあと、**アプリを再度開く手間なく**アップロードが完了すること  
3. 設定およびアップロード時のダイアログで、**「今すぐ送る / Wi-Fi 待ち」をユーザーが制御**できること（デフォルトは「今すぐ」）  
4. 既存のアルバム Web アプリ（Cloudflare Workers + R2 + D1）の API・データモデルを大きく変えずに実現すること  

対象外（この計画ではやらない）:

- Web のみでの「再オープン不要」の完全達成（技術的に不可に近い）  
- カメラロール全体の自動バックアップ（Google Photos 型）。本アプリは**手動でアルバムに追加**するモデルを維持する

## Why（なぜ React Native でラップするのか）

### ユーザー課題の本質

「Wi-Fi のときだけ上げたい」は手段であり、本質は次の同時達成である。

| 条件 | 内容 |
|------|------|
| P1 | 通信料をかけない（任意でモバイルデータを使わない） |
| P2 | Wi-Fi 復帰後に、アプリ再オープンなどの手間をかけない |

P1 だけなら Web のキューでも近似できる。**P2 まで含めると Web では足りない。**

### Web / 現行スタックだけでは足りない理由

| 能力 | Web / PWA | ネイティブ（RN シェル） |
|------|-----------|------------------------|
| ファイルを端末に保持して後送 | IndexedDB 等で可能 | 可能 |
| Wi-Fi / 非従量回線のみで実行 | 判定が弱く、特に iOS で不安定 | OS 制約（例: Android `UNMETERED`）で可能 |
| アプリ終了後も転送継続 | iOS は Background Sync 非対応。Android も限定的 | iOS `URLSession` 背景転送 / Android `WorkManager` 等 |

アップロード対象のバイナリは**まだ端末上**にある。Cloudflare Queues 等は「サーバー到達後の処理」向けであり、**端末回線を待って送る問題は解けない。**

### なぜ React Native か

- 既存 UI / ビジネスロジック（Web）を **WebView または段階的移植**で活かしやすい  
- バックグラウンドアップロードとネットワーク種別は **ネイティブモジュール** に任せられる  
- 完全なネイティブ再実装（別アプリ化）より、現行 Cloudflare バックエンドを維持したまま P1+P2 に届ける現実的な経路になる

## How（どう実現するか）

### 全体アーキテクチャ

```
[React Native シェル]
  ├─ UI: 既存 Web を WebView で表示（初期）または画面単位で RN 化
  ├─ アップロード設定（モバイルデータ許可 / 毎回確認）
  ├─ ローカルキュー（端末ストレージ）
  └─ ネイティブ Uploader
        ├─ iOS: background URLSession（Wi-Fi 制約）
        └─ Android: WorkManager + NetworkType.UNMETERED 等
              │
              ▼  Wi-Fi（または許可時はモバイル）で PUT
        既存 Presigned URL → R2
              │
              ▼
        既存 photos metadata API（Workers / D1）
```

サーバー側（Cloudflare Workers / R2 / D1）の契約は原則維持する。

```
POST upload-url → PUT（R2）→ POST photo metadata
```

Presigned URL はキュー消化・転送開始の直前に取得する（有効期限切れ対策）。

### UX（確定済み方針）

| 項目 | 内容 |
|------|------|
| デフォルト | **今すぐアップロード**（モバイルデータ利用を許可） |
| 設定 | 「モバイルデータでアップロード」トグル、「追加時に毎回確認する」トグル |
| ダイアログ | 毎回確認 ON、またはモバイルデータ OFF かつ非 Wi-Fi のときに「今すぐ / Wi-Fi で後で」 |
| 待機中 | 「Wi-Fi 待ち N 件」「今すぐ送信」「キャンセル」 |

### 実装フェーズ

#### Phase 0 — 検証

- [ ] RN プロジェクト骨格（既存リポジトリ隣接 or monorepo）  
- [ ] WebView で現行本番 / ステージングを表示できること  
- [ ] ネイティブ Uploader で Presigned URL への PUT がバックグラウンド継続するか（iOS / Android 実機）  
- [ ] ネットワーク制約（Wi-Fi only）が期待どおりか  

#### Phase 1 — P1+P2 の最小実装

- [ ] メディア選択後、ファイルをアプリ領域へコピーしてキュー登録  
- [ ] 設定トグル（デフォルト: 今すぐ / 毎回確認 OFF）  
- [ ] 条件に応じたダイアログ  
- [ ] ネイティブ Uploader による R2 PUT + 完了後 metadata POST  
- [ ] 待機ステータス UI と手動「今すぐ送信」  

#### Phase 2 — 配布・運用

- [ ] App Store / Google Play 申請・証明書・更新フロー  
- [ ] クラッシュ・アップロード失敗の観測  
- [ ] Web 単体利用との機能差の明示（シェル利用を推奨する範囲）  

#### Phase 3 — 任意の改善

- [ ] WebView 依存の縮小（アップロード周辺を RN 画面へ）  
- [ ] 設定のアカウント同期（D1）  
- [ ] 失敗リトライ方針の精緻化  

### リスクと対策

| リスク | 対策 |
|--------|------|
| iOS 背景転送の審査・Background Modes | 必要最小の mode に限定。公式ドキュメントに沿って設定 |
| 電池最適化で Android が止まる | フォアグラウンド通知 / ユーザー向け案内 |
| Presigned URL 期限切れ | 転送開始直前に再発行 |
| WebView とネイティブキューの二重管理 | アップロード開始の単一入口をネイティブ側に寄せる |
| ストア配布の運用負荷 | Phase 0 で実機検証してから配布準備に進む |

### 成功条件（受け入れ）

1. モバイルデータ OFF のとき、セルラーではアップロードが開始されずキューに入る  
2. その後 Wi-Fi に接続し、**アプリを開かなくても**（OS が許可する範囲で）送信が完了する  
3. モバイルデータ ON（デフォルト）では、従来どおり選択直後に送信できる  
4. 設定およびダイアログで動作を上書きできる

## 参考（技術的根拠の要約）

- iOS Safari / 全 WebKit ブラウザ: Background Sync / Background Fetch 非対応 → タブ終了後の自動送信不可  
- Android Chrome: Background Sync は限定的。Wi-Fi 専用の OS 級制約は WorkManager の方が明示的  
- 本アプリのアップロードはクライアント起点の R2 Presigned PUT であり、サーバー非同期に置き換えても端末通信は発生する
